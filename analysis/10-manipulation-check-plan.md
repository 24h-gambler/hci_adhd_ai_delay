# 10 · 조작 점검 계획 (결과 절 맨 앞에 들어갈 내용)

이 절이 없으면 **"정말 지연이 입력과 무관했나?"를 반박당한다.**
있으면 conventional 조작이 성립했다는 증거가 된다.

`analysis/manipulation_check.py`가 아래 검사를 자동으로 수행한다.

---

## 1. 핵심 검사 — 입력 길이와 부과 지연의 독립성 ★

### 무엇을 보는가

각 턴에서 **사용자 입력 글자 수**와 **실제로 부과된 지연**의 상관.

```
imposed_delay_ms = display_ts − user_input_submit_ts
```

### 왜 0이어야 하는가

목표 지연 D는 사용자가 전송한 **직후에** 조건별 범위에서 무작위로
뽑는다. 입력 텍스트를 보기 전이므로 D는 입력과 통계적으로 독립이다.
이것이 conventional 조작의 정의다.

반대로, LLM 응답이 온 **뒤부터** D초를 세면 총 지연이
`LLM 생성 시간 + D`가 되고, LLM 생성 시간은 입력 길이를 따라간다.
그러면 지연이 입력에 대한 **index signal**이 되어버려
"입력한 글의 길이나 내용과 무관하게 결정한다"는 전제가 무너진다.

### ★ 어떤 상관을 봐야 하는가 — 전체 상관은 함정이다

**조건을 무시한 전체 상관을 보면 안 된다.**

지연의 전체 분산은 조건 간 차이(1.5초 / 8.5초 / 18초)가 압도적으로 지배한다.
그 안에서 입력 길이가 만드는 변동은 묻혀 버린다. 그래서 **구현이 틀려도
전체 상관은 0 근처로 나온다.**

`manipulation_check.py --demo-broken`이 이를 재현한다
(LLM 응답이 온 뒤부터 D초를 세는 잘못된 구현).

| 통계량 | 올바른 구현 | **잘못된 구현** |
| --- | --- | --- |
| 조건 무시 전체 r | −.055 | **−.044 ← 정상으로 보인다** |
| **조건 내 부분상관 r** | .019 | **.120 ← 잡힌다** |
| 조건별 r · 즉시 | .045 | **.265 ← 잡힌다** |
| 조건별 r · 중간 | −.028 | **.221 ← 잡힌다** |

> 위 수치는 **합성 데이터로 검사기의 동작을 보인 것**이지 실제 데이터가 아니다.

**따라서 보고할 값은 조건을 통제한 부분상관이다.**
각 조건 안에서 입력 길이와 지연을 조건 평균으로 중심화한 뒤 상관을 낸다
(자유도는 추정한 조건 평균 수만큼 차감).

### 판정 기준

> ⚠️ 아래는 사전에 정해 두는 **기준**이지 예상값이 아니다.
> 실제 수치는 데이터를 봐야 안다.

| 판정 | 기준 |
| --- | --- |
| 통과 | **조건 내 부분상관** \|r\| < .10 **그리고** 조건별 \|r\|이 모두 < .10 |
| 참고 | 95% CI가 (−.10, .10) 안에 들어가는가 — 표본 크기에 좌우된다 (아래) |
| 실패 | 어느 하나라도 \|r\| ≥ .10 → 구현을 의심한다 |

### 신뢰구간과 표본 크기 — 등가성을 "입증"하려 하지 말 것

Fisher z에서 CI 반폭은 `1.96 / √(N−3)`이다. 따라서

```
CI ⊂ (−b, b) 를 만족하려면   N ≥ 3 + ( 1.96 / (atanh(b) − |atanh(r)|) )²
```

b = .10일 때 r ≈ 0이면 **N ≈ 388턴**, r = .03이면 **N ≈ 790턴**,
r = .05이면 **N ≈ 1,500턴**이 필요하다.
참가자 1명이 분석 가능한 턴 30개(5턴 × 6대화)를 만드므로,
r이 조금만 커져도 현실적인 표본으로는 CI 기준을 만족할 수 없다.

**그래도 문제되지 않는다.** D는 입력 텍스트를 보기 전에 난수로 뽑히므로
**모상관은 설계상 정확히 0**이다. 이 검사는 등가성을 통계적으로 입증하려는
것이 아니라 **구현이 설계대로 됐는지 확인하는 것**이다. 잘못된 구현은
r이 .2 이상으로 나오므로 어떤 표본 크기에서도 눈에 띈다.

스크립트는 CI 기준을 **참고 지표(△)**로만 표시하고 종료 코드에 반영하지
않으며, 필요한 N을 함께 출력한다.

### 논문 서술 (수치는 실제 값으로 채운다)

> 지연은 각 턴에서 사용자 입력을 처리하기 전에 조건별 범위에서 무작위로
> 추출되었으므로 입력 내용과 독립적이다. 이를 확인하기 위해 조건을 통제한
> 상태에서 사용자 입력 길이와 실제 부과된 지연의 부분상관을 산출했다.
> 그 결과 r = __, 95% CI [__, __] (턴 N = __)로 사전에 설정한 등가 한계
> ±.10 안에 있었다. 조건별로도 즉시 r = __, 중간 r = __, 긺 r = __로
> 모두 한계 안이었다.

### 이 검사의 두 번째 쓸모 — 구현 오류를 잡아낸다

`|r|`이 크게 나오면 거의 항상 **코드가 틀린 것**이다. 확인 순서:

1. D를 **입력 전송 후 즉시** 뽑고 있는가, LLM 응답 후에 뽑고 있는가
2. 대기 시작점 t0가 **전송 시각**인가, LLM 응답 도착 시각인가
3. 스트리밍이 켜져 있지 않은가 (`prompts/prompts.yaml: stream: false`)
4. 표시 시각을 `t0 + D`로 계산하는가, `now + D`로 계산하는가

## 2. 조작 충실도 (manipulation fidelity)

| 검사 | 기준 | 실패 시 |
| --- | --- | --- |
| 실제 지연이 목표 D에 도달했는가 | \|imposed − target\| ≤ 250 ms | 타이머 정확도 문제 |
| LLM이 D보다 오래 걸린 턴 | 0에 가까울수록 좋음 | 그 턴은 조작 실패 → 분석에서 별도 처리 |
| 조건별 지연 분포가 설정 범위 안에 있는가 | 100% | 난수 범위 설정 오류 |
| 안전 경로 발동 턴 | 지연 미적용 확인 | `materials/04 §5` |

**LLM 지연 초과 턴 처리**

- 논문에 **"조작 충실도"로 비율을 보고한다.** 감추지 않는다.
- 5% 미만이면 포함하고 민감도 분석을 붙인다. 그 이상이면 사전에 정한
  규칙에 따라 제외한다. **규칙은 데이터를 보기 전에 정한다.**

### ★ "즉시" 조건이 실행 불가능할 수 있다 — 파일럿 1순위 확인 사항

이 설계에서 **가장 먼저 깨지는 것은 긺 조건이 아니라 즉시 조건이다.**

즉시 조건의 목표 지연은 1.0~2.0초다. 그런데 300 토큰 응답을 생성하는 LLM의
지연은 흔히 그보다 길다. LLM이 목표 시각보다 늦게 도착하면 `t0 + D`에
표시할 수 없고, 그 턴의 지연은 **LLM 생성 시간을 따라가게 된다.**
LLM 생성 시간은 입력 길이를 따라가므로, 그 순간 즉시 조건에서만 지연이
입력에 연동되고 **조건별 상관 검사에서 즉시 조건의 r만 튀어 오른다.**

`manipulation_check.py`가 이를 자동으로 검사한다.

```
조건 실행 가능성 (LLM 생성 시간 분포 vs 목표 지연 하한)
  LLM 생성 시간 p50 __ms · p95 __ms · max __ms
  ✗ 즉시  하한 1000ms < p95 __ms
```

**대응 (파일럿 결과에 따라 택일)**

| 대응 | 비용 |
| --- | --- |
| 즉시 조건 하한을 LLM p95 위로 올린다 (예: 2.5~3.5초) | "즉시"라는 이름이 무색해진다. 조건 간 대비는 유지된다 |
| 프롬프트의 문장 수 규칙을 조인다 (2~4문장 → 2~3문장) | 응답이 짧아져 상담 맥락이 약해질 수 있다. `max_tokens`를 조이면 문장 중간에서 잘리므로 그쪽은 안 된다 — `materials/04 §6` |
| 더 빠른 모델로 바꾼다 | 응답 품질이 달라진다 → 파일럿을 다시 한다 |
| 즉시 조건만 "도착 즉시 표시"로 정의한다 | ✗ **권하지 않는다.** 그 조건에서 conventional 전제가 깨진다 |

→ 파일럿에서 **LLM 응답 시간 분포를 먼저 측정한 뒤** 세 조건의 범위를
확정한다. 범위를 바꾸면 `prompts/prompts.yaml`의 `delay_conditions`와
`manipulation_check.py`의 `TARGET_RANGE_MS`를 **함께** 고친다.
→ `OPEN_QUESTIONS.md` Q12.

## 3. 응답 내용 통제 확인

| # | 검사 | 기대 | 의미 |
| --- | --- | --- | --- |
| ① | 조건 간 **AI 응답 길이** | **차이 없음** | 통제 성공 |
| ② | 조건 간 **AI 응답 유사도** | **높음** | 조건이 내용에 영향을 주지 않았음 |
| ③ | **맥락 간** AI 응답 유사도 | **낮음 (달라야 함)** | 맥락 조작 성공 |
| ④ | 조건 간 **사용자 입력 길이** | 달라도 됨 | ★ 아래 참조 |

### ④가 다른 것은 문제가 아니다 — 오히려 결과다

긴 지연 조건에서 사용자가 짧게 쓴다면, 그것은 통제 실패가 아니라
**발견**이다. 지연이 사용자의 발화 행동을 바꾼 것이다.
같은 논리로 **다음 입력을 시작하기까지의 시간**도 종속변인으로 다룬다.

### ①②③의 유사도 측정에 대하여

`manipulation_check.py`는 **문자 바이그램 Jaccard**로 계산한다.
가볍고 의존성이 없지만 어휘 표면만 본다.

> 논문에 싣는 수치는 **문장 임베딩 코사인 유사도**로 다시 계산할 것을
> 권한다 (예: 다국어 문장 임베딩 모델). 스크립트의 값은
> **파일럿 중 빠른 점검용**이다.

## 4. 프롬프트 동일성 확인

로그의 `prompt_sha256`으로 자동 검사한다.

| 검사 | 기대 |
| --- | --- |
| 같은 맥락 안, 지연 조건 3수준 | **해시가 모두 같아야 함** |
| 맥락 A vs 맥락 B | **해시가 달라야 함** |
| 참가자 간 `prompt_version` | 모두 같아야 함 (섞이면 데이터가 갈린다) |

같은 맥락 안에서 해시가 다르면 **지연 조건이 프롬프트에 영향을 준 것**이고,
그 순간 조작 분리가 무너진다. 이 검사는 실패 시 즉시 중단 사유다.

## 5. 시간 추정의 정확도 (조작 점검이자 결과)

조건별 설문 문항 ①(`materials/05`)과 실제 지연을 비교한다.

```
추정 오차     = 추정 초 − 실제 평균 지연 초
추정 비율     = 추정 초 ÷ 실제 평균 지연 초
```

- **조작 점검으로서**: 조건 간 추정값이 단조 증가하지 않으면
  참가자가 조건 차이를 전혀 지각하지 못했다는 뜻이다.
- **결과로서**: 과대·과소 추정 패턴이 집단(ADHD 경향 여부)과
  맥락에 따라 다른가 — 이것이 이 연구의 관심사 중 하나다.

## 6. 로그 스키마

`manipulation_check.py`가 읽는 JSONL. 한 줄 = 한 턴.

| 필드 | 형 | 설명 |
| --- | --- | --- |
| `participant_id` | str | P01 … |
| `group` | str | 집단 (adhd / comparison) |
| `block` | int | 1 / 2 |
| `conversation_index` | int | 1~6 (진행 순서) |
| `condition` | str | immediate / medium / long / practice |
| `context` | str | a / b |
| `turn_index` | int | 1~5 |
| `practice` | bool | 연습 턴이면 true (분석 제외) |
| `user_input_start_ts` | int | epoch ms — 첫 타자 입력 |
| `user_input_submit_ts` | int | epoch ms — **전송 시각 = t0** |
| `user_input_text` | str | 원문 |
| `user_input_chars` | int | 공백 포함 글자 수 |
| `target_delay_ms` | int | 뽑은 목표 지연 D |
| `llm_request_ts` | int | epoch ms |
| `llm_response_ts` | int | epoch ms |
| `display_ts` | int | epoch ms — 화면 표시 |
| `ai_response_text` | str | |
| `ai_response_chars` | int | |
| `finish_reason` | str | LLM 종료 사유. `"length"`면 응답이 잘린 것 = 결함 |
| `next_input_start_ts` | int/null | 다음 턴 첫 타자 (마지막 턴은 null) |
| `safety_flag` | bool | 안전 경로 발동 |
| `manipulation_ok` | bool | 조작 성공 여부 (앱이 판정) |
| `prompt_version` | str | v0.1 |
| `prompt_sha256` | str | build_prompts.py 출력 |
| `model` | str | 모델 ID |
| `temperature` | float | |
| `max_tokens` | int | |

**파생값** (스크립트가 계산)

```
imposed_delay_ms        = display_ts − user_input_submit_ts
llm_latency_ms          = llm_response_ts − llm_request_ts
user_response_latency_ms= next_input_start_ts − display_ts
typing_ms               = user_input_submit_ts − user_input_start_ts
```

## 7. 사용법

```bash
# 합성 데이터로 스크립트 동작 확인 (실제 데이터 없이)
python3 analysis/manipulation_check.py --demo          # 올바른 구현 → 통과
python3 analysis/manipulation_check.py --demo-broken   # 잘못된 구현 → 검출

# 실제 로그
python3 analysis/manipulation_check.py logs/session_P01.jsonl
python3 analysis/manipulation_check.py logs/*.jsonl --json > check.json

# 등가 한계를 바꿔서 (기본 0.10)
python3 analysis/manipulation_check.py logs/*.jsonl --equivalence-bound 0.15
```

종료 코드: 통과 `0` / 검사 실패 `1` — CI나 파일럿 스크립트에 물릴 수 있다.
